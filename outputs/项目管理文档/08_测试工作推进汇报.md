## 汇报结构框架与叙述重点（导览页）

本报告按测试工作实际的**推进时间序**组织，采用「三阶段递进 + 一条贯穿线」框架：

```
阶段一 单元测试          →  阶段二 集成测试          →  阶段三 探索性测试
（函数/算法正确性）        （模块间链路与服务间协作）     （真实用户视角找盲区）
        └────────── 贯穿线：自动化断言回归资产沉淀（每次迭代必跑）──────────┘
```

**三个叙述重点**（向老师讲清楚的核心信息）：

1. **测试是随架构演进的，不是一次性动作**——三个阶段分别回应了三个不同层面的风险：代码算错、模块接不上、界面藏问题；
2. **每一阶段都有"发现的问题"作为转折证据**——用真实缺陷案例说明测试产生了价值，而非走过场；
3. **量化结果可复核**——所有通过率数字都有脚本和提交记录支撑，欢迎抽查。

## 一、测试策略总览

### 1.1 系统构成决定的测试分层

LTPMS 是「Java 后端 + Vue3 前端 + Python AI 微服务 + MySQL」的四组件系统，且带 AI 生成 SQL 的不确定环节，因此测试策略为：

| 层 | 对象 | 手段 | 工具 |
|---|---|---|---|
| 单元测试 | 纯函数、算法、SQL 校验器 | JUnit / pytest | 断言驱动 |
| 集成测试 | API 链路、导入管线、服务间调用、数据库迁移 | HTTP 断言脚本 + pytest 打真库 | Python requests / TestClient |
| 端到端/验收 | 权限矩阵、页面渲染 | Playwright E2E + 权限断言集 | cjs 脚本 + 截图取证 |
| 探索性测试 | 真实 UI 操作路径、异常环境 | 手动 + 半自动，发现问题回写为自动化用例 | 浏览器 + 实机 |

### 1.2 一条铁律

**每个已确认的缺陷，必须回沉为一条可重复执行的自动化断言**——这让回归测试从"重新人肉点一遍"变成"跑一遍脚本"，是后期迭代提速的关键。

## 二、阶段一：单元测试——先把"算得对不对"钉死

### 2.1 测试范围

优先覆盖**纯逻辑、高风险、无依赖**的单元，即"一旦算错、全链路数据都不可信"的部分：

| 单元 | 为什么必须测 | 用例数 |
|---|---|---|
| 周次计算（WeekMath） | 奇偶周、周次范围字符串解析决定课表与开放时段是否正确，是全系统最易算错的一块 | 12 |
| 专业解析（MajorExtractor） | 从班级名自动解析专业，是课程数据自动化的入口 | 3 |
| 课程服务（CourseService） | 课程聚合是课表→实验→报表的中间层 | 7 |
| SQL 校验器（nlq-service） | AI 生成的 SQL 必须先过"只读白名单"，这是安全底线 | 覆盖于 test_sql_validator |
| 权限过滤（nlq-service） | AI 查询必须按角色裁剪可见范围 | 覆盖于 test_permission |

**后端 JUnit 共 4 个测试类 23 个用例；AI 微服务 pytest 共 16 个文件 165 个用例**（含 Agent 循环、工具注册、技能加载、记忆存储、向量嵌入、视觉识别等模块级测试）。

### 2.2 主要工作内容

- 为周次计算建立**边界用例矩阵**：`1-8周`、`1-16单周`、`1-16双周`、跨周区间、非法输入等，全部用参数化断言；
- 为 SQL 校验器做**对抗性用例**：多语句拼接、注释绕过、DDL/DML 关键字变形，验证一律拒绝；
- pytest 全程**不 mock 数据库**（见 §3.2 原则延伸），服务层测试打真实 MySQL 实例。

### 2.3 发现的问题与改进

| 问题 | 发现方式 | 改进与成效 |
|---|---|---|
| 周次解析对「单双周」后缀处理错误，导致课表时间槽错位 | WeekMathTest 边界用例 | 修正解析规则，12 条用例全过并锁定为回归项 |
| 班级名→专业解析对多班级逗号串只取第一个 | MajorExtractorTest 用例 | 改为解析全部班级取众数 |

**阶段结论**：单测阶段的价值不在覆盖率数字，而在于把"数据正确性的地基"钉死——后面集成和探索阶段再没出现过"算错数"类缺陷返工。

## 三、阶段二：集成测试——验证"接起来跑不跑得通"

### 3.1 测试范围

| 链路 | 验证内容 | 手段 |
|---|---|---|
| Excel 导入管线 | 上传→POI 解析→逐行 upsert→导入回执（成功/新建账号/失败原因） | Python 验收脚本批量打接口 |
| 账号联动 | 陌生学号自动建档、默认密码、首登强制改密、**学号撞工号拒绝**（r2-C2 规则） | 构造撞号夹具实测 |
| 数据库迁移 | 7 份 upgrade 脚本 + 2 份 rollback 脚本逐份执行回退 | 实库演练，迁移必配回滚成为规约 |
| 服务间协作 | backend↔nlq-service 内部 token 鉴权、只读账号第四层防护 | 冒烟脚本（mcp_smoke、stage3 系列） |
| 权限矩阵 | 三角色 × 全接口的读写边界 | 权限断言集：**75/75 通过**（ADMIN 越权写实验项目必须 403） |
| 页面渲染 | 实验项目列表页在 1527×900 无遮挡、导入模板入口常驻可点 | Playwright E2E：**28/28 通过**，截图取证 |
| 视觉识别链路 | 图片分派、意图路由、改道覆盖 | AC 验收 **14/14**，稳定性重试 **4/4**，降级通道 **3/3** |

### 3.2 主要工作内容与原则

- **对接真实环境，不 mock 数据库**。集成层测试全部打真实 MySQL（含导入、迁移、回滚），理由：本项目最大风险恰恰是"环境差异型"缺陷（字符集、GBK、文件占用），mock 会系统性掩盖它们；
- **验收脚本化**：教师课程管理、开放管理等模块各配一份验收脚本（如 `acceptance_course_mgmt_b1.py`），需求文档里的每条 AC 对应一组断言，跑完即出通过率；
- **破坏性测试纳入清单**：撞号导入、重复导入、归档项目写操作、越权访问等"故意使坏"场景有固定用例集，每次大版本回归必跑。

### 3.3 发现的问题与改进

| 问题 | 影响 | 改进与成效 |
|---|---|---|
| 模块合并后遗留旧路由，管理员侧可绕过只读限制 | 权限旁路 | 权限断言集补齐 + 前端菜单同步收口，回归 **78/78** |
| 归档后任务仍可编辑（软约束漏判） | 数据完整性 | 状态机入口统一加 `requireActive` 校验，入断言集 |
| 智谱视觉通道下线导致识别链路中断 | 功能不可用 | 统一切换 deepseek-flash，同时保留 `VISION_PROVIDER` 回退开关并实测降级 3/3 通过 |
| Windows 环境三连坑：.bat 被 GBK 解析、jar 被旧进程占用致打包失败、超时命令在重定向下不可用 | 环境搭建即失败，阻塞一切测试 | 沉淀为脚本编写规约（纯 ASCII 注释、端口幂等探测、ping 等待），全套启动脚本重写 |

**阶段结论**：集成阶段消灭的全部是"接缝处"的缺陷——权限旁路、状态漏判、通道切换、环境陷阱，没有一条是单测能发现的，印证了分层的必要性。

## 四、阶段三：探索性测试——用真实用户的眼睛找盲区

### 4.1 触发原因

自动化全绿之后，我刻意发起一轮**不带脚本、以教师/管理员真实操作习惯走查系统**的探索。动机：断言只能验证"我想到的"，找不到"我没想到要测的"。

### 4.2 主要工作内容

- 以三类角色身份分别完成完整任务动线（学期初始化、课题全流程、学生答题链路）；
- 从**入口可见性、空态呈现、异常文案、极端数据**四个维度走查每个页面；
- 所有发现按「是否可自动化」分类：能固化的回写为断言/E2E 用例，不能固化的写入开发规约。

### 4.3 发现的典型问题（两个代表性案例）

**案例一：路由存在 ≠ 功能可达。** 「制度与流程」知识库页面的路由、接口、权限在合入时全部测试通过，但开发者漏挂了侧栏菜单项——从用户视角这个功能**等于不存在**，只能手输 URL 才进得去。自动化 100% 绿，用户视角功能"丢"了。

**案例二：状态白名单漏配导致布局塌陷。** 顾问作答卡片上线时，新状态没加入布局的"激活态白名单"判定，结果是态的卡片按 DOM 顺序掉到页面最底部，空态机头、示例卡一并露出。这是视觉回归，接口断言永远测不出。

**共性根因**：两者都是"登记型"缺陷——新资源落地时漏了一步登记。改进因此不止于修点，而是修面：**验收标准从"接口通过"升级为"真实 UI 点击主路径可达"**，并把这两个案例固化为 E2E 必测项。

### 4.4 成效

- 探索期发现的缺陷全部回沉为自动化用例，此后同类缺陷零复发；
- 形成「功能合入检查单」：菜单入口、状态白名单、空态、权限、回滚脚本五项逐条过，成为提交前门禁。

## 六、反思与下一步

**三点反思**：

1. 测试投入的边际价值排序为：探索性测试 > 集成断言 > 单元测试数量。单测保住了下限，但真正改变系统气质的是后两层；
2. 「不 mock 真库」的决策成本是环境搭建变重，收益是拦掉了全部环境差异型缺陷——对交付型学生项目是值得的取舍；
3. 自动化测试的可信度来自"可复核"：断言脚本、截图、Git 记录三位一体，任何数字老师都可以现场抽查。

**下一步两项计划**：

- 把探索性测试从"里程碑式突击"改为"每迭代固定 2 小时走查"制度，走查发现继续回沉自动化；
- 当前单测在 Service 层覆盖仍薄（主要覆盖算法与工具类），下学期初前补齐导入管线与权限判定核心路径的 Service 级 JUnit，目标新增 30+ 用例。
